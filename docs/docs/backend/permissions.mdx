# Permissions & RBAC

Route-level RBAC: every endpoint declares `permission=` on `SecureRouter`. This is **not** object-level ownership — see [Tenancy](./tenancy.mdx) for row scoping.

## Permission string

```text
{resource}:{action}
```

Actions (`platform_kit.rbac.Action`): `read` | `list` | `create` | `update` | `delete` | `approve` | `export`.

`PUBLIC` skips auth (review carefully). Wildcards in role maps: `"*"`.

## Default roles (`ROLE_PERMISSIONS`)

| Role | Grants |
|---|---|
| `admin` | `["*"]` |
| `member` | tenant list/update; user create/list/read/update; role list/read; permission list; plan list; subscription read; full item + category CRUD |
| `viewer` | tenant list; user list/read; role list/read; permission list; audit list; plan list; subscription read; item + category read/list |

`ROLE_PERMISSIONS` is the **bootstrap seed + code fallback**. On SaaS, live grants come from `roles` / `permissions` / `role_permissions` and are embedded in the access JWT at issue time.

System roles (`admin` / `member` / `viewer`) are shared and **immutable** via the IAM admin APIs — customize by creating **tenant** roles.

## Resolution chain

`PermissionResolver`:

1. Prefer `permissions` claim on the access token (when present)
2. Redis cache (when available)
3. DB loader (`roles` / `role_permissions` / `permissions`)
4. Fallback to code `ROLE_PERMISSIONS`

Mutating roles/permissions should invalidate the resolver cache for that role name.

## TEN001

If a model table has `tenant_id`, handlers that touch it must bind tenant context via `TenantIdDep` / `principal.tid` / `PlatformOperatorDep`, or explicitly mark `# dx: cross-tenant`.

## Dev tokens

```bash
uv run dx token core-api --all
uv run dx token core-api --perm 'identity.tenant:list' --perm 'core-api.item:read' --ttl 3600
uv run dx permissions core-api
```

`permissions.py` is **protected** — leads only (`DX_ALLOW_BASELINE=1`).
