# Routing & auth

## Fixed core routes

These are part of the baseline — do not reinvent them:

| Route | Purpose |
|---|---|
| `/login` | Authentication entry |
| `/` | App shell / home |
| `/settings` | Theme, locale, density, color preset |
| `/forbidden` | 403 |
| (not-found) | 404 via router `notFoundComponent` (not a dedicated `/not-found` path) |

Product routes (e.g. `/items`, `/items/$itemId`) live under feature `routes/`.

## Permissions

Non-core routes declare a `permission` (items example: `items:list`, `items:read`). The shell uses the authenticated principal’s grants to show/hide nav and guard pages.

## Auth status in the example SPA

Current `web-spa` login is a **dev stub**:

- Fake principal + `dev-token`
- Storage keys:
  - `aham.auth.token`
  - `aham.auth.principal` (required by router + `AuthProvider`)
- Does **not** call `/api/v1/auth/login` on the SaaS monolith

API client attaches `Authorization: Bearer <token>` from `aham.auth.token` when calling `VITE_API_BASE_URL`.

Wiring real auth against `mono-monolith` is the natural next integration step (see [Connecting to the API](./connecting-api.mdx)).
